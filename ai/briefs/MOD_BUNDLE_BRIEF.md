# Brief: write the OKF bundle for one mod (tier-1 coordinator)

You are a tier-1 research coordinator. Your job is to analyze ONE Kitten Space Agency (KSA) mod
repository exhaustively and write its OKF knowledge bundle under
`/Users/asherwin/repos/meow-sci/ksa-coffer/content/mods/<mod-slug>/`, plus a machine-readable feature
catalog at `/Users/asherwin/repos/meow-sci/ksa-coffer/ai/catalog/<mod-slug>.yml`.

The audience is community modders who want to learn how a feature was done and recreate it. KSA uses
a bespoke engine (Vulkan renderer, ImGui UI, Bepu physics, FMOD audio, Harmony-patched via the StarMap
loader); nothing from Unity, Unreal or KSP applies. The decompiled game sources are the only ground
truth for engine behavior.

1. `/Users/asherwin/repos/meow-sci/ksa-coffer/docs/content-conventions.md` - layout, frontmatter,
   lifecycle vocabulary, code-reference and snippet rules. Follow it exactly.
2. `/Users/asherwin/repos/meow-sci/ksa-coffer/ai/briefs/REPOS.md` - pinned repo table (slug, web URL,
   ref, license) and the game assemblies location.
3. `/Users/asherwin/repos/meow-sci/ksa-coffer/.claude/skills/okf/SKILL.md` - OKF v0.2 rules.

5. Game sources for every engine claim: `/Users/asherwin/repos/meow-sci/ksa-game-assemblies/current/decomp/`.

## What "exhaustive" means

Catalog every novel thing the mod does that another modder could reuse. A feature is one reusable
mechanism, not one button. Examples of the right grain: "transpile the ComputeDrag call site to replace
stock drag", "draw great-circle lines on the sky with the ImGui background draw list", "register a
custom XML asset type", "mount a live camera on a part and show it in a secondary viewport", "persist
mod state as a sidecar next to the native save", "load a custom font into ImGui", "wait for the vehicle
solver before mutating vehicle state", "export a contract assembly for other mods via
ExportedAssemblies". Include infrastructure features (logging, settings, config, hotkeys, ModMenu
integration, build/deploy/test tooling) when they show a technique others would copy. Expected counts:
small mod 3-8 features, medium 8-20, large 20-60. Monorepos (unscience) get a `submods/` directory
with one `Submod` concept per sub-mod plus a flat `features/` directory with feature slugs prefixed by
the sub-mod slug (`graffiti-decal-painting.md`).

## Lifecycle and timing is mandatory

The user cares most about WHEN each feature runs in the KSA frame and physics loop. For every feature,
determine the exact hook (StarMap attribute, Harmony patch target and kind, event, own thread), map it to
the `lifecycle` vocabulary in the conventions, and explain in `## Lifecycle and timing` what state is
safe to read or write there and why the mod chose that point. Check `Program.OnFrame`,
`Program.PrepareFrame`, `Universe.ExecuteNext*Solvers` / `Apply*Solvers`, `Program.OnDrawUi*`,
`Program.RenderGame` in the decomp and `StarMap.Core/Patches/ProgramPatcher.cs` for where the StarMap
attributes actually fire. Several repos carry their own analysis of this (KSACars/KSAGolf/KSArmory
`docs/KSA-FRAME-ORDER.md`, unscience `scope/*.md`, gatOS `docs/KSA_INTEGRATION_MATRIX.md`); use them as
leads, then confirm against the decomp.

## Deliverables

```
content/mods/<mod-slug>/
  index.md                 generated by build_indexes.py
  log.md                   newest-first history with a Creation entry for today
  overview.md              type: Mod
  features/index.md        generated
  features/<feature>.md    type: Mod Feature, one per feature
  submods/<submod>.md      type: Submod (monorepos only)
ai/catalog/<mod-slug>.yml  feature catalog (schema below)
```

`overview.md` body (headings at `##`): what the mod is and who made it; install footprint (mod.toml
contents, manifest id, assets, folder layout); loader model and entry class with a table of the
lifecycle hooks it uses and what each does; dependencies (StarMap, Harmony, KittenExtensions,
ShaderExtensions, ModMenu, native libs) and how they are resolved; architecture summary (main
subsystems, threads, data flow); `## Features` table linking every feature concept with its category and
lifecycle; build, test and tooling notes; compatibility notes (KSA build the repo says it targets, known
breakage patterns); `## Secondary sources` listing analysis docs inside the repo worth reading. Frontmatter
per conventions with `repos` (this repo, and any other repo cited) and `game`.

`features/<feature>.md` body per conventions: intro, `## How it works`, `## Lifecycle and timing`,
`## Key code` (table: path link, role), `## Snippets` (verbatim, path comment first line, <= 40 lines
each, 1-4 snippets), `## Game APIs touched` (type.member with decomp link and what it is for),
`## Pitfalls and version notes`, `## See also` (other features in this mod; other mods only if the file
exists). Frontmatter: `type`, `title`, `description`, `mod`, optional `submod`, `category` (one),
`tags`, `techniques`, `game_types`, `lifecycle`, `hooks`, `generated`, `status`, `repos`, `game`,
`sources` (every cited file with `repo`, `path`, `resource`, `title`).

## Rules

- Use absolute paths. Write only inside `content/mods/<mod-slug>/` and `ai/catalog/<mod-slug>.yml`.
- Never invent an API, a file path, a line number or a behavior. If you could not verify a claim in
  the checkout or the decomp, leave it out or mark it `(unverified)` and say why.
- Every snippet is copied from the checkout. Every linked path exists. Every GitHub link is pinned to
  the ref in REPOS.md.
- `generated: { by: claude-code/opus-5.5, at: <date -u +%Y-%m-%dT%H:%M:%SZ> }` on every concept.
  Never add `verified`.
- Body headings start at `##`. One `description` sentence, no trailing period, quoted if it contains
  a colon.
- Do not run git commands that change state (no commit, no checkout). Do not touch other mods'
  directories or the bundle root indexes.
